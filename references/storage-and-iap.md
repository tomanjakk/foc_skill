# 校准数据存储与 IAP 升级

## 存储接口及职责

先根据目标存储器和现有代码确定接口；下表是**需要覆盖的职责清单，不要求新增一套同名 API**。地址使用目标介质约定的偏移或绝对地址，调用方与实现必须一致；长度、擦除单位、编程对齐和可访问区域由目标硬件确定。复用现有接口时先检查其参数、执行上下文和返回语义。

### 存储器底层

| 接口职责 | 输入和行为 | 结果与约束 |
|---|---|---|
| 初始化 / 就绪检查 | 初始化所需总线、控制器及写保护；检查设备是否可访问 | 区分成功、未初始化、忙、超时和通信故障；不能因初始化成功就假定数据有效。 |
| 读取 | 给定地址、目标缓冲区和字节数，读取指定范围 | 检查空指针、长度、地址范围及溢出；失败不得将缓冲区当成有效记录。 |
| 擦除（需要擦除的介质） | 给定目标擦除区，按芯片的页或扇区操作 | 事先确认完整物理擦除范围属于授权分区；不越过边界或擦除其他记录。EEPROM 不应为了统一接口强行模拟 Flash 擦除。 |
| 写入 / 编程 | 给定地址、数据和长度；按器件要求执行分页、对齐和编程 | EEPROM 处理页边界、写保护和写周期；Flash 检查擦除状态、最小编程单位和设备限制，处理超时、失败及锁定恢复。 |
| 写后核验 | 需要验证时读回并与预期数据比较，或计算并比较完整性值 | 返回核验结果；不把底层写成功等同于数据已通过核验。 |

需要时增加就绪轮询或后台服务，但不要把阻塞擦写放在高速控制中断。接口要让调用方区分参数错误、越界、未就绪、超时、擦写失败和校验失败，并明确失败时数据状态可能不确定；不要静默忽略错误。

### 校准记录接口

| 接口职责 | 函数应完成的事 |
|---|---|
| ADC 校准保存 / 读取 | 保存或恢复三相 ADC 零偏；读取时校验记录版本、完整性、有效性及目标允许范围。 |
| 编码器校准保存 / 读取 | 保存或恢复方向、偏移、零位和补偿表等实际算法所需字段；检查表长度、版本、范围和完整性。 |
| 保存请求 / 后台处理 / 结果查询 | 如果采用异步保存，复制或确保待写数据生命周期，提交请求后由后台执行；定义忙、完成和失败如何被调用方观察，防止请求覆盖或丢失。请求已接受不等于持久化成功。 |
| 有效性检查 / 清除 | 启动时仅将完整且通过校验的记录标为有效；清除必须限定对应数据区并按用户授权执行。有效标志不能替代完整性检查。 |

原工程已有 `FOC_Port_Save/LoadAdcCalibration`、`FOC_Port_Save/LoadEncoderCalibration`、`FOC_Port_Is*CalibrationValid` 和清除接口；底层有 `EEPROM_Init/Read/Write`、`EEPROM_RequestAdcSave`、`EEPROM_RequestEncoderSave` 及后台 `EEPROM_Calib_Service`。当前板级保存接口提交请求后返回成功，**不能把该返回值解释为写入完成**；现有 `Is*Valid` 是否足以表达本次请求的完成与失败，应按调用链核查，不能假定它是保存完成回执。

### IAP 存储接口

| 接口职责 | 函数应完成的事 |
|---|---|
| 区域及镜像范围检查 | 校验 App 起止、长度、地址加法溢出、擦除和编程对齐；确保完整物理擦写区不碰驻留程序、有效标志以外的保留区、参数或校准数据。 |
| 清除升级有效标志 | 开始覆盖旧应用前，使其不再被认为有效；核对标志所在的整个擦除单元只包含可被擦除的数据。 |
| 擦除目标镜像区 | 基于已检查的镜像范围确定实际擦除单元，报告硬件错误；不得把通信长度直接当作未经核查的擦除范围。 |
| 接收并写入块 / 核验块 | 检查期望地址、块长度和顺序；编程后读回比对并返回成功或失败。掉电、失败和重复请求的行为必须由协议明确。 |
| 镜像完整性检查 | 根据协议核对完整镜像长度与校验值，必要时验证来源；逐块读回、镜像 CRC 与认证分别描述，不能互相替代。 |
| 写入和读取有效标志 | 仅在必需的镜像检查成功后写入有效状态，并读回确认；定义标志写入中断时的启动行为。 |
| 检查启动条件 / 跳转 | 检查有效状态与向量表、栈和入口范围，按目标芯片处理外设、中断、VTOR 与 MSP，再跳转；明确失败时留在哪个状态。 |

GD 工程实际接口及其实现边界见下方实例。整包 CRC、认证和重试能力必须分别核对，不能仅凭职责清单认定已实现。

## 校准数据存储规则

移植 FOC 时，ADC 校准数据和编码器校准数据按以下优先级选择非易失存储位置：

1. 目标板有适用的外部非易失存储空间（如 EEPROM）时，优先保存在外部存储器中。
2. 没有适用的外部非易失存储空间时，使用目标 MCU 内部 Flash：ADC 校准数据放在物理 Flash 倒数第二页，编码器校准数据放在物理 Flash 倒数第一页。此处页指芯片规定的实际擦除单位；芯片使用扇区或不等大小擦除单元时，根据手册确认对应区域，不自行假定页大小或地址。

### 移植检查

- 依据目标 MCU 手册、实际 Flash 容量、Bank、擦除单位和地址映射计算位置；确认所选区域可用、容量足够，且与 Bootloader、App、IAP、参数及其他保留区不重叠。检查链接脚本、工程配置和下载擦除策略，确保固件更新不会意外覆盖校准数据。如果存在冲突或空间不足，停止并报告，不能静默改用其他地址或覆盖数据。
- 外部存储器同样核对容量、地址范围、分页写入、写保护、写周期及与其他记录的分配，不能因器件存在就假定空间可用。
- 按实际存储介质处理擦除、对齐、最小编程单位、写入顺序及失败状态；检查中断和控制实时性，不在高频控制中断内执行阻塞式擦写。
- 记录格式应有数据有效性与完整性校验、版本识别及失效处理；评估掉电中断擦写、损坏数据和重复写入寿命。单页方案不自动保证掉电时旧数据可恢复，不能宣称具备掉电原子性。
- 保持 FOC 对 ADC 与编码器校准的保存、读取和有效状态接口语义一致。原工程的保存请求由后台处理；提交请求不等于写入成功。移植时核实调用链、完成状态和上电加载结果。
- 对新旧固件格式兼容和已有数据保留进行核对；缺少信息时明确询问，不能自动擦除或覆盖校准数据。电机 R/L、齿槽表、控制参数等其他数据的存储位置不由本规则指定，需单独核对。

### 验证

先做地址范围、接口调用及记录格式的静态检查。根据用户授权，再分别验证保存成功或失败的反馈、复位或重新上电后的加载与数据有效性；需要验证掉电恢复时，按目标硬件设计单独测试。源码检查、编译和实机验证分别报告，不互相替代。烧录、复位、擦写和设备采集均需相应授权。

## IAP 升级移植与验证

根据目标工程的实际需求、通信协议、MCU 手册和 Flash 布局分析或实现 IAP。先确认升级范围及 Bootloader、App、有效标志、参数和校准数据所在区域；信息不足时列出待确认项，不假定地址、镜像格式或通信方式。移植时先检查现有实现和调用链，复用满足要求的机制。

实现前必须整理并核对完整存储分配表：每种存储器的容量和擦除单位，以及 Boot、App1、App2、升级暂存区、升级状态/有效标志、ADC 和编码器校准、其他参数、齿槽表等各项数据的起止地址、大小、所有者与擦写方式；对未使用或未确认的项目明确标注。核对链接文件、实际生效的工程配置、固件地址限制、上位机和下载器擦除策略。参照下方已有工程实例，其地址是历史实例，不能直接套用到新目标。

### Flash 分区和校准数据

- 按目标芯片的实际 Flash 容量、Bank、擦除单位和编程对齐确定各区域，检查链接脚本、向量表地址、镜像最大长度及下载配置。镜像范围和每次擦除范围都不得与受保护区域重叠。
- ADC 和编码器校准的存储优先级及内部 Flash 后两页规则见 本文校准数据存储规则。如果校准数据位于内部 Flash，IAP 擦写必须保留这些页；若在外部存储器，也要检查是否与升级暂存区或其他记录冲突。
- 如果现有分区、升级方式或下载器擦除设置无法满足保护要求，停止并报告冲突，不静默调整分区或擦除数据。更新 Bootloader 和 App 的权限、范围分别确认。

### 接收、校验和生效

- 明确起始地址、长度、分包顺序、完整性校验及失败返回；检查地址运算、越界、重复包、丢包和通信中断的处理。完整性校验不能代替固件来源认证；需要防止未授权固件时，根据产品要求单独设计认证机制。
- 根据目标硬件的存储空间和升级方案定义接收、擦写、校验和生效顺序。只有确认所需数据写入并验证成功后才能标记有效或跳转；区分下载完成、镜像校验成功和启动成功。
- 检查异常断电、镜像不完整、校验失败及升级中断后的启动行为和恢复路径。单分区覆盖可能无法保留旧 App，不应承诺自动回滚；只有实现并验证了对应机制才可宣称支持。
- 跳转前检查目标向量表、栈指针、复位入口和地址范围，并依据目标 MCU 和工程确认中断、外设、时钟与向量表切换要求。不能仅凭标志位判断镜像可启动。

### 验证与操作边界

先静态核对分区、链接与边界，再按需求验证正常升级、边界长度、错误校验、通信中断及异常恢复。应检查升级前后校准数据及其他受保护数据；重启、擦写、下载和通信到设备须有用户对相应操作的明确授权。分别报告源码检查、编译、离线测试和实机验证结果；没有执行的项目明确标为未验证。

### GD32 工程 IAP 实例和移植经验

此实例来自 GD32F303RCT6 的当前源码静态分析；用户说明该方案实际使用过，但本次未核验具体实机升级记录，不能把当前源码版本的断电恢复和回滚写成已实测通过。地址只适用于此实例；目标工程必须重新制定和核对完整存储分配表。

#### 必须有两个工程

1. **Boot 工程**：从芯片复位入口运行；初始化升级所需时钟、CAN、看门狗和状态存储，检查 App1 的向量表及完整镜像 CRC；接收新镜像到 App2、校验、逐页交换、记录状态、处理重启恢复及必要的回滚，最后跳转固定地址 App1。此工程是纯 Boot，不承担正常 FOC 运行。
2. **App 工程**：链接和运行在 App1 固定地址，实现正常电机控制。收到回 Boot 请求后，先按板级实现停机，写备份寄存器请求并复位；新固件在约定的初始化阶段完成后，通过备份寄存器提交试运行确认并复位，由 Boot 将状态转为 IDLE。确认时机由产品实际自检要求确定，不能仅把执行到某行作为电机功能已验证。

Boot 与 App 共用 `Common/ota_layout.h` 的分区和状态协议；上位机是第三个协作组件，负责镜像准备和 CAN 升级，不是 MCU 上的第三个工程。App2 是暂存和旧镜像备份区域，App 镜像仍按 App1 地址链接，不直接从 App2 执行。两工程的链接地址、VTOR、协议、状态格式、看门狗及升级镜像必须匹配。

#### 现有 Flash 划分

`ota_layout.h` 定义 256 KiB Flash、2 KiB 页；以下地址范围包含首尾，须结合芯片配置、链接文件和实际固件确认：

| 区域 | 地址 | 用途 |
|---|---|---|
| Boot | `0x08000000–0x08009FFF` | 独立驻留程序，40 KiB |
| 状态页 A | `0x0800A000–0x0800A7FF` | OTA 记录页 |
| App1 | `0x0800A800–0x08021FFF` | 固定运行区，94 KiB |
| App2 | `0x08022000–0x080397FF` | 下载新镜像；交换后保存旧镜像，94 KiB |
| 临时页 | `0x08039800–0x08039FFF` | 单页交换缓冲 |
| 状态页 B | `0x0803A000–0x0803A7FF` | 另一 OTA 记录页 |
| 预留区 | `0x0803A800–0x0803E7FF` | 16 KiB，具体用途须核对 |
| 参数及校准 | `0x0803E800–0x0803FFFF` | 6 KiB；Boot/IAP 应保护，具体记录以 App 存储实现为准 |

分区地址来自 `Common/ota_layout.h`；原工程地图对预留区大小写作 32 KiB，但按地址差为 16 KiB，以实际地址计算为准。上位机固定镜像长度 `0x17800`（96256 B），不足部分填 `0xFF`，完整镜像包含填充值参与校验。下载前还要核对实际链接产物和下载器擦除设置；保护区不能只靠表格保证。

#### CAN 升级与存储接口

- 当前设备端使用标准 CAN `0x700` 接收、`0x601` 回复；流程版本 `0x02`。上位机以 `0x33` 确认版本，必要时通过 App 的 `0xA5` 请求复位进 Boot。
- `0x01` 提交固定镜像大小及流程版本；Boot 在 App2 擦除并记录下载状态。`0x31` 的逻辑地址从 App1 递增，设备映射到 App2；`0x32` 带 16 位分片号，每片最多 5 字节，按片 ACK/NACK，整块写入后读回比较。部分重复分片有内容比对处理；末片 ACK 丢失等边界需专项验证，不可概括为所有重试均幂等。
- `0xBD` 携带全镜像 CRC32；接收完整 47 块后，Boot 验证 App2 固定全区 CRC 和按 App1 链接地址解释的向量表，然后提交交换状态。CRC 检测传输/存储错误，不提供固件来源认证。
- `can_flashing_erase_pages`、`can_flashing_program_block`、`can_flashing_copy_page` 分别负责擦页、编程及读回、页复制；`Ota_State_Crc32` 和 `Ota_State_Load/Commit/Compact` 负责 CRC、读取及提交/整理状态记录。函数命名和范围属于此代码版本，移植先复查定义与调用方。

#### 交换、掉电恢复与回滚

每页依次执行 App1 → 临时页、App2 → App1、临时页 → App2；每个阶段复制和读回成功后提交状态，再推进下一阶段。状态记录含序号、阶段、页号、试运行次数、镜像 CRC 和记录 CRC，两个状态页交替追加；整理时先在另一页保存有效记录，再擦旧页。重启时读取最新有效状态，按已提交阶段继续交换。实际断电时 Flash 的擦写特性及所有中断点仍需验证。

下载期间 App1 不参与擦写；若状态显示下载未完成，启动时丢弃 App2 元数据并检查 App1。交换完成后新镜像位于 App1、旧镜像位于 App2，进入 PENDING_CONFIRM；Boot 每次试启动先记录次数，App 完成约定初始化后写确认并复位，Boot 再提交 IDLE。超过 3 次未确认或新 App 校验无效时，Boot 先检查 App2，再尝试按同样的页交换回滚；首次安装没有旧镜像时无法回滚，应留在 Boot。实际确认依赖备份寄存器及供电条件；复位与彻底掉电表现需分别测试。

重点验证状态记录写入、目标页擦除/编程、每个交换阶段完成前后、试运行确认和回滚各处掉电；同时核对下载失败、片 ACK 丢失、整包 CRC 错误和参数/校准区保持。不得根据状态机设计直接宣称任意时刻断电均可恢复。

依据文件：`Common/ota_layout.h`、Boot 的 `Hardware/can_flashing.c`、`Hardware/ota_state.c`、`User/main.c`，App 的 `Hardware/can_flashing.c`、`User/main.c`，以及上位机 `iap_hex.py`、`iap_can_upgrade.py`。移植前重新核对这两个工程和上位机的实际版本，不依赖其他机器上的绝对路径。
